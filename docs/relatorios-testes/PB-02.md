## Defeitos encontrados

### DEF-PB02-01 — Refresh de token e sinalização de reauth não implementados
- **Severidade: Alta** · Caso: CT-PB02-06
- `spotify_client` só tem `get_auth_url`, `exchange_code_for_token`, `get_current_user_profile`.
  Não há renovação de access token expirado nem escrita em `reauth_required_at` (a coluna existe,
  morta). O access token expira em ~1h e o sistema não consegue renovar → PB-08/PB-14 ficarão sem
  token válido.
- **Reprodução:** `hasattr(spotify_client, 'refresh_access_token')` → False; teste CT-PB02-06 falha.
- **Recomendação:** implementar `refresh_access_token(refresh_token)` e um caminho central que, ao
  falhar o refresh, seta `reauth_required_at` e sinaliza reautenticação.

### DEF-PB02-02 — Chave Fernet efêmera quando `FERNET_KEY` ausente
- **Severidade: Alta** · Caso: CT-PB02-05 (integridade/persistência)
- `crypto._get_fernet()` gera uma **chave temporária em memória** quando `FERNET_KEY` não está no
  ambiente (que é o default do `.env.example`, vazio). Tokens ficam cifrados com uma chave que muda
  a cada reinício → após restart, `decrypt` lança `InvalidToken`: tokens **irrecuperáveis**.
- **Reprodução (confirmada):** encrypt → reset da instância (simula restart) → decrypt → `InvalidToken`.
- **Impacto:** dá falsa sensação de "criptografia ok" mas quebra persistência real; mascara erro de
  configuração com um simples `warning`.
- **Recomendação:** exigir `FERNET_KEY` (falhar no startup se ausente em produção), nunca gerar chave
  volátil silenciosamente.

### DEF-PB02-03 — Comparação naive/aware quebra o path de sessão em SQLite
- **Severidade: Média** · Casos: CT-PB02-03/04 (no harness SQLite)
- `AppSession.expires_at`/`token_expires_at` são `DateTime(timezone=True)`. Em SQLite o valor volta
  **naive**; o código faz `app_session.expires_at < datetime.now(timezone.utc)` (aware) → `TypeError`
  → 500 em `/auth/me`. Em Postgres (TIMESTAMPTZ) funciona.
- **Impacto:** os testes de API do PB-02 **não rodam** no harness SQLite previsto no `PLANO_TESTES.md
  §4`; fragilidade de portabilidade e ausência de normalização de timezone na leitura.
- **Recomendação:** normalizar para aware ao comparar (tratar valor sem tz como UTC) ou padronizar o
  harness de API em Postgres.

### DEF-PB02-04 — `.env` com nome de chave errado quebra o fluxo OAuth real
- **Severidade: Média** · Caso: fluxo e2e real
- O `.env` local guarda o segredo sob `CLIENT_SECRET` (não `SPOTIFY_CLIENT_SECRET`), então
  `settings.spotify_client_secret` = None → `exchange_code_for_token` levanta `ValueError` →
  callback responde **400**. O login real não completa. (Não versionado; era DEF-PB01-02, agora com
  impacto funcional.)
- **Recomendação:** alinhar as chaves do `.env` ao `.env.example`/`config.py`.

### DEF-PB02-05 — Entrega sem testes automatizados
- **Severidade: Média** (processo)
- Nenhum teste de auth foi entregue (só `test_health.py`), violando `AGENTE_IMPLEMENTACAO.md §6`.
  Os CT-PB02-* ficariam eternamente "Não executado". O QA teve de criar `test_pb02_auth_qa.py`.

### DEF-PB02-06 — Desvios menores
- **Severidade: Baixa**
- (a) `/auth/login` responde **307** (RedirectResponse default), enquanto o CT-PB02-01 previa 302.
- (b) `redirect_url` (`http://127.0.0.1:5173`) e `secure=False` **hardcoded** no callback — deveriam
  vir de configuração.
- (c) callback não trata `?error=access_denied` (usuário nega consentimento) → 422 por `code`
  obrigatório, em vez de erro amigável.

### DEF-PB02-07 — Scope creep (frontend Home)
- **Severidade: Baixa** (processo)
- `frontend/src/Home.jsx` (tela Home é do PB-04) foi adicionada/estilizada durante o PB-02, violando
  `AGENTE_IMPLEMENTACAO.md §5.4` (não antecipar PBs futuros).
