## Testes adicionais executados

Criado `backend/tests/test_pb08_music_snapshots_qa.py` (**21 testes, autoria do QA**). Todos
**aprovados** — inclusive o que documenta o DEF-PB08-01.

**Isolamento entre usuários (não exigido pelo plano, mas crítico para privacidade):**
- Snapshot de A nunca vaza para B; cada usuário recebe o seu, e o de A permanece intacto no banco.
- Cache fresco de A **não** satisfaz o pedido de B (o cache não é global por engano).

**Fronteira do TTL:** 6d23h59 → `cached=true`; 7d01min → refetch; 30d → refetch. O TTL vem da
configuração e não está fixo no código (com `music_snapshot_ttl_days=1`, snapshot de 2 dias é
recoletado).

**Privacidade:** nem a resposta nem o snapshot persistido contêm access token, refresh token ou o
token fictício do mock; o corpo expõe apenas os nove campos do contrato.

**Reauth:** usuário sem token gravado recebe 401 controlado (nunca 500); com reauth pendente e cache
fresco, o snapshot continua servindo sem tocar o Spotify.

**Entradas inválidas:** `time_range` inválido (`ontem`, vazio, `MEDIUM_TERM`, `1 year`, `all_time`) →
422 sem chamada externa. As três faixas temporais convivem sem sobrescrever uma à outra (3 snapshots).

**429 não corrompe estado:** um 429 no meio da coleta (tracks OK, artists limitado) não grava
snapshot pela metade — as faixas antigas permanecem.

**Criterio 1 — escopo de endpoints, verificado por varredura do código-fonte inteiro:** os únicos
endpoints da Web API chamados são `GET /v1/me` (PB-02, escopo `user-read-private`) e
`GET /v1/me/top/{tracks,artists}` (PB-08, escopo `user-top-read`). Nenhuma chamada a
`/recommendations`, `/audio-features` ou outros endpoints fora do MVP. O `item_type` é validado
contra um conjunto fechado antes de entrar na URL, então não há interpolação arbitrária.

**Migração em PostgreSQL real**, ciclo executado pelo QA: `upgrade head` → `0005_pb08_music_snapshots`
cria `user_music_snapshots` com PK UUID, FK `user_id` com `ON DELETE CASCADE`, índice
`ix_user_music_snapshots_user_id` e unicidade `uq_music_snapshot_user_range (user_id, time_range)`;
`downgrade 0004_pb06_context_mode` remove a tabela (`to_regclass` → NULL); `upgrade head` reaplica sem
erro. Reversibilidade comprovada.

## Defeitos encontrados

### DEF-PB08-01 — Coleta concorrente do mesmo usuário resulta em HTTP 500

- **Severidade:** **Média** (avaliada explicitamente abaixo; não bloqueia a aprovação)
- **Caso de teste relacionado:** nenhum obrigatório; encontrado em teste exploratório de concorrência
- **Ambiente:** PostgreSQL 16 real (duas sessões concorrentes) e reprodução determinística em SQLite
- **Pré-condições:** usuário autenticado, sem snapshot para a faixa temporal (ou com snapshot vencido)
- **Passos para reprodução:**
  1. Disparar duas chamadas simultâneas de `GET /me/top` (ou dois `POST /me/refresh-music-snapshot`)
     para o **mesmo** usuário e a **mesma** `time_range`.
  2. Ambas executam `_find_snapshot` → `None` antes de qualquer commit e seguem para o `INSERT`.
- **Resultado esperado:** as duas requisições concluem; a perdedora reaproveita o snapshot gravado
  pela vencedora (padrão já adotado em `join_room`).
- **Resultado observado:** a vencedora grava; a perdedora recebe
  `IntegrityError: duplicate key value violates unique constraint "uq_music_snapshot_user_range"`,
  não tratado, resultando em **HTTP 500 "Internal Server Error"**.
- **Evidência:** script de concorrência contra PostgreSQL real →
  `RESULTADO: OK snapshot` / `RESULTADO: IntegrityError: ... uq_music_snapshot_user_range` /
  `SNAPSHOTS NO BANCO: 1`. Confirmação do status na camada HTTP → `HTTP STATUS: 500`.
  Teste determinístico:
  `test_qa_concurrent_first_collection_returns_500_instead_of_handling_conflict`.
- **Arquivos possivelmente relacionados:** `backend/app/services/music_service.py:108-122`
  (`get_or_refresh_snapshot`), sem `except IntegrityError` no `db.commit()`.
- **Impacto:** duplo clique em atualizar, duas abas abertas ou retry do cliente podem devolver 500 ao
  usuário. **O banco não é corrompido** — a restrição de unicidade segura o estado e resta exatamente
  um snapshot. A resposta é genérica ("Internal Server Error"), **sem vazar stack trace** ou dados
  internos. Uma nova tentativa funciona normalmente, pois o snapshot já existe e o cache responde.
- **Recomendação de correção:** aplicar o mesmo padrão já usado em
  `room_service.join_room` — envolver o commit em `try/except IntegrityError`, fazer `db.rollback()`,
  reler o snapshot e devolvê-lo. É o tratamento que o próprio repositório já adota para esta classe de
  conflito em `create_room` e `join_room`.
- **Status:** **Aberto**

**Avaliação explícita da severidade Média (exigida pelo processo).** Classifiquei como Média e não
Alta porque: não viola nenhum dos cinco critérios de aceitação; não corrompe dados nem quebra a
consistência do banco; não expõe informação sensível; não bloqueia o fluxo principal; e se resolve
sozinho na tentativa seguinte. Classifiquei como Média e não Baixa porque é um caminho de erro
genuinamente não tratado que chega ao usuário como 500, numa classe de conflito que o repositório já
sabe tratar em dois outros serviços — é uma inconsistência real de robustez, não algo cosmético.

Hoje o alcance é limitado: o PB-08 não entregou frontend, então o gatilho prático é uso direto da API
ou duplo disparo. **Recomendo corrigir antes da validação integrada da Sprint 1**, porque o critério 4
("snapshot vencido atualizado antes da geração") indica que o fluxo de geração vai consumir estas
rotas, ampliando a janela.

## Limitações da validação

- **A integração real com o Spotify não foi validada e não pode ser considerada aprovada.** Todos os
  caminhos externos são mockados, conforme o plano e as regras do projeto. O contrato assumido
  (endpoints, parâmetros `time_range`/`limit`/`offset`, semântica do `Retry-After` no 429, formato
  `{"items": [...]}`) foi conferido apenas contra o código e a documentação citada pelo implementador,
  **não contra a API real**. Um mock que passa não prova que o Spotify se comporta assim.
- Os testes do PB-08 **não** foram submetidos a teste de mutação nesta rodada, diferentemente do que
  fiz no PB-06. A confiança neles vem da inspeção: CT-PB08-02 usa uma função que lança se chamada, e
  as asserções conferem o estado no banco, não apenas o corpo da resposta.
- Concorrência entre **usuários diferentes** não foi exercitada; pela chave
  `(user_id, time_range)` não há conflito esperado, mas isso é análise, não medição.
- Não há frontend para o PB-08 nesta entrega, então não houve verificação de interface.
